## Задание 7. Проектирование схем коллекций для шардирования данных

### Коллекция Orders

В качестве шард ключа я выбрал хешированный идентификатор клиента.

Плюсы:
- наилучшее распределение
- общий для клиента, его заказов и корзины, а значит данные клиента, корзина и заказы окажутся скорее всего на одном шарде

Минусы:
- затрудненный точечный поиск по другим полям, например по идентификатору заказа
- нет поддержки диапазонов

Какие альтернативы рассматривались:
- Геошардирование - с учетом масштабов компании, не выглядит как хороший вариант, вряд ли геозон очень много, и скорее
всего будет большой перекос в сторону пары-тройки крупных, которые перегрузят соответствующие шарды.
- По статусу заказа - активные заказы на одном шарде, завершенные на другом (в т.н холодном хранилище),
отмененные на третьем (ледяное хранилище), звучит соблазнительно, но быстро получим перегруженные шарды, тк пропорции
активных заказов к неактивным с ростом числа заказов будет все более не в пользу активных.
- По идентификатору заказа - хороший вариант, но у идентификатора клиента есть связь с другими сущностями - профиль клиента,
корзина заказов.

```
{
    "order_id": ObjectId, 
    "user_id": "string",
    "items": [
        {
            "product_id": "string",
            "quantity": NumberInt,
            "price": NumberDecimal
        }
    ],
    "status": "pending|confirmed|shipped|delivered|cancelled",
    "total": NumberDecimal,
    "shipping_address": { ... },
    "created_at": ISODate,
    "updated_at": ISODate
}

sh.shardCollection("shop.orders", { "user_id": "hashed" })
db.orders.createIndex({ user_id: 1, order_id: 1 },{ unique: true })
db.orders.createIndex({ user_id: 1, status: 1 })
```

### Коллекция Products

1. Я произвел вертикальное партицирование по идентификатору товара - остатки товара вынес в отдельную коллекцию inventory.
К inventory применил геошардирование по составному шард-ключу - идентификатор товара, геозона.

Товары имеют очень большое количество чтений, относительно чтений - записей немного, это позволит нам максимально быстро
без блокировок читать товары и позволит независимо, точечно и быстро обновлять остатки. 
Геошардирование остатков может быть связано со складской инфраструктурой в конкретной геозоне,
также позволит облегчить нагрузку на запись на мастер шардах.

Минусы:
- сложность реализации
- необходимость поддержания согласованности

```
{
    "product_id": "string",
    "region": "string",
    "quantity": NumberInt,
    "updated_at": ISODate
}

sh.shardCollection("shop.inventory", { "region": 1, "product_id": 1 })
db.inventory.createIndex({ region: 1, product_id: 1 },{ unique: true })
```

2. Для оставшейся коллекции products в качестве шард ключа я выбрал хешированный идентификатор товара.

Плюсы:
- наиболее равномерное распределение

Минусы:
- наиболее востребованные товары не получат преимущества по сравнению с менее востребованными

```
{
    "product_id": "string",
    "name": "string",
    "category_id": "string",
    "price": NumberDecimal,
    "created_at": ISODate,
    "updated_at": ISODate,
    "attributes": [...]
}

sh.shardCollection("shop.products", { "product_id": "hashed" })
```
