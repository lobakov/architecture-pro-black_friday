## Задание 7. Проектирование схем коллекций для шардирования данных

### Коллекция Orders

В качестве шард ключа я выбрал хешированный идентификатор клиента.

Плюсы:
- наилучшее распределение
- общий для клиента, его заказов и корзины, а значит данные клиента, корзина и заказы окажутся скорее всего на одном шарде

Минусы:
- затрудненный точечный поиск по другим полям, например по идентификатору заказа
- нет поддержки диапазонов

Какие альтернативы рассматривались:
- Геошардирование - с учетом масштабов компании, не выглядит как хороший вариант, вряд ли геозон очень много, и скорее
всего будет большой перекос в сторону пары-тройки крупных, которые перегрузят соответствующие шарды.
- По статусу заказа - активные заказы на одном шарде, завершенные на другом (в т.н холодном хранилище),
отмененные на третьем (ледяное хранилище), звучит соблазнительно, но быстро получим перегруженные шарды, тк пропорции
активных заказов к неактивным с ростом числа заказов будет все более не в пользу активных.
- По идентификатору заказа - хороший вариант, но у идентификатора клиента есть связь с другими сущностями - профиль клиента,
корзина заказов.

```
{
    "order_id": ObjectId, 
    "user_id": "string",
    "items": [
        {
            "product_id": "string",
            "quantity": NumberInt,
            "price": NumberDecimal
        }
    ],
    "status": "pending|confirmed|shipped|delivered|cancelled",
    "total": NumberDecimal,
    "shipping_address": { ... },
    "created_at": ISODate,
    "updated_at": ISODate
}

sh.shardCollection("shop.orders", { "user_id": "hashed" })
db.orders.createIndex({ user_id: 1, order_id: 1 },{ unique: true })
db.orders.createIndex({ user_id: 1, status: 1 })
```

### Коллекция Products

1. Я произвел вертикальное партицирование по идентификатору товара - остатки товара вынес в отдельную коллекцию inventory.
К inventory применил геошардирование по составному шард-ключу - идентификатор товара, геозона.

Товары имеют очень большое количество чтений, относительно чтений - записей немного, это позволит нам максимально быстро
без блокировок читать товары и позволит независимо, точечно и быстро обновлять остатки. 
Геошардирование остатков может быть связано со складской инфраструктурой в конкретной геозоне,
также позволит облегчить нагрузку на запись на мастер шардах.

Минусы:
- сложность реализации
- необходимость поддержания согласованности

```
{
    "product_id": "string",
    "region": "string",
    "quantity": NumberInt,
    "updated_at": ISODate
}

sh.shardCollection("shop.inventory", { "region": 1, "product_id": 1 })
db.inventory.createIndex({ region: 1, product_id: 1 },{ unique: true })
```

## Задание 8. Выявление и устранение «горячих» шардов

1. Метрики. 

Стоит подумать как о технических метриках, так и о бизнес-метриках.
- Технические:
 - Утилизация CPU > 80%
 - Disk IOPS > 80% IOPS используемого диска
 - Mongo поддерживает счетчики операций (insert, update, query)
 - Количество открытых соединений
- Бизнес-метрики:
 - Периоды пикового спроса
 - Популярность товаров
 - Комбинации товаров ("с этим товаром покупают также...")

2. Механизмы автоматического перераспределения.

С учетом поставленной задачи, о том что шард содержащий категорию товаров "Электроника" стал перегруженным,
других механизмов кроме изменения ключа шарда придумать не могу. Именно поэтому в шардировании товаров я не выбрал
шардирование по категориям, потому что легко получить дисбаланс. Единственный выход тут изменить ключ шардирования.
Никакая перебалансировка тут не поможет, потому что большую категорию невозможно будет разбить.

Я знаю, что с некоторой версии Mongo есть механизмы автоматического перераспределения, позволяющие изменить ключ
шардирования на лету. Но для большого объема данных это вероятно будет очень медленная операция.

## Задание 10. Миграция в Cassandra

### 10.1

Наиболее критичными с точки зрения целостности для нас являются сущности Carts и Inventory, неконсистентность данных в корзине
может серьезно повлиять на намерение приобрести товар, а неактуальные остатки в момент распродажи могут принести проблемы по результатам торговли.

Наиболее очевидным кандидатом является коллекция Products, тк она обновляется нечасто, но при этом у нее высочайшая нагрузка на чтение.
Коллекция Orders же терпит eventual consistency с небольшой задержкой, особенно с учетом того, что большинство заказов в списке будут завершенными.

### 10.2

Не работал с кассандрой, а в уроке тема кластерных ключей и прочего раскрыта слабо, поэтому воспользовался помощью интернета.

#### Коллекция Products

Ключ партицирования остается тем же - product_id.
Дополнительная таблица для поиска товаров по категориям.

```
-- Основная таблица товаров
CREATE TABLE products (
    product_id   TEXT,
    name         TEXT,
    price        DECIMAL,
    category_id  TEXT,
    attributes   MAP<TEXT,TEXT>,
    created_at   TIMESTAMP,
    updated_at   TIMESTAMP,

CREATE TABLE products_by_category (
    category_id   TEXT,
    product_id    TEXT,
    name          TEXT,
    price         DECIMAL,
    created_at    TIMESTAMP,
    PRIMARY KEY (category_id, product_id)
);
```

### 10.3

Cassandra поддерживает использоваине всех механизмов сразу, можно настроить и hinted-handoff и read-repair, одновременно,
вопрос в настройках

Для Orders можно настроить агрессивный read repair и максимальное окно для hinted handoff, для Products оба этих механизма
можно сделать менее агрессивными чтобы не влиять на чтение.
Anti-entropy repair для обеих коллекций можно сделать более частым инкрементальным (например каждый день) и редким полным (раз в неделю).
